Case Study

Making Deep Q-Learning Visible in the Browser

I built CartPole Control Lab around a simple goal: keep the learning mechanics inspectable. The browser simulation shows the changing state, selected actions, replay memory, exploration rate, episode scores, and manual controls while the Python notebook remains available as the source-side learning implementation.

The problem

A notebook can contain the complete training loop and still be difficult to understand at a glance. CartPole depends on four continuously changing observations, two possible actions, delayed consequences, and repeated training updates. I wanted the public interface to expose those pieces without pretending that GitHub Pages can execute Python, Gym, or Keras.

Requirements I preserved

  • Use the CartPole-v1 environment and its four-value observation space.
  • Keep the two-action left/right control model.
  • Preserve the DQN structure of two 24-unit ReLU hidden layers and a two-value linear output.
  • Keep the documented hyperparameters: gamma 0.95 , learning rate 0.001 , replay capacity 1,000,000 , batch size 20 , and epsilon decay from 1.0 toward 0.01 .
  • Keep experience replay and epsilon-greedy action selection visible in the project.
  • Preserve the established DQN behavior while keeping external starter-code and environment sources explicitly attributed.

Browser architecture

The public project is static HTML, CSS, and JavaScript, so it can run on GitHub Pages. The browser simulation implements CartPole dynamics locally and uses a small JavaScript DQN agent. It does not execute the Python notebook or Keras model in the browser.

assets/js/ MODULES 
config.js          shared model and environment constants
cartpole-env.js    CartPole physics and terminal-state handling
replay-buffer.js   fixed-capacity circular replay memory
dqn-agent.js       action selection, replay, and network updates
app.js             controls, rendering, metrics, and page events

Why the browser agent keeps a compatibility mode

The browser DQN defaults to legacy training mode because changing its update order or training additional layers would change the existing demo behavior. I keep that compatibility path explicit instead of silently replacing it. A separate full-backprop mode is available in the agent implementation for a complete gradient update, but the public demo does not enable it by default.

Engineering tradeoff: preserving the existing browser-learning behavior matters more here than changing the agent simply to use a different implementation. The compatibility decision is documented and regression-tested.

Replay memory and performance

The earlier browser demo memory used an array and removed the oldest item with shift() . With a capacity of one million experiences, repeatedly shifting a large array is unnecessary work. I replaced that storage mechanism with a fixed-capacity circular buffer. It still discards the oldest experience when full, but it does so without moving every remaining item.

Termination and validation

The environment keeps the existing terminal value used by the application and also reports terminated and truncated separately. That makes the reason an episode ended clearer without breaking the existing control flow. Unsupported actions are rejected with a descriptive error instead of silently being treated as a left move.

Interface and accessibility

The interface uses semantic buttons for simulation controls, visible keyboard focus, pressed-state information for the agent/manual mode controls, an aria-live training log, and reduced-motion handling. Manual mode works with both the on- screen force buttons and the left/right arrow keys. Shared site styles are separated from page-specific styles so visual changes have a predictable owner.

Testing strategy

The automated tests focus on deterministic behavior: environment reset and termination, invalid actions, replay-buffer capacity, DQN output shape, preservation of legacy first-layer behavior, the opt-in full-backprop path, required DOM hooks, stylesheet ordering, and static project references. I avoid tests that claim the randomly initialized learning agent must reach a particular score, because that would make the suite depend on stochastic training outcomes.

Runtime boundaries

The GitHub Pages experience is the browser demo. My original Python/Jupyter project is maintained under original-project/ and runs separately with Gymnasium, Keras/TensorFlow, NumPy, and Matplotlib. The source includes its required score logger, and the DQN/logger starter lineage is cited in the repository.
